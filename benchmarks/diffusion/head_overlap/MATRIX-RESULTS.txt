Issue #10448: unprofiled model comparisons (2026-11-20)

H3-Image FP8 SP4 is the clearest accepted offline sweet spot: 3072^2
and 4096^2 reduced full-request median latency by 4.38% and 3.01%.
Each won all 30 interleaved pairs; RGB outputs matched at seeds 42/43/44.
This qualifies the explicit fixed-shape graph probe, not default HTTP serving.

Measurement and scope
NVIDIA L20X; NV18 peers; torch 2.14.0+cu130; batch/concurrency 1.
Timing spans Omni.generate and includes text encoder, DiT and VAE. Image/video
extraction, hashes and persistence follow the timer. No profiler wraps these runs.
Both variants warm in one process. Request pairs alternate serial/overlap order.
The table reports (median(serial)-median(overlap))/median(serial), not the median
of paired percentages. Both sample arrays and paired saving are in the JSON.
serial1: one head group using optimized direct CE and owned output storage.
overlap2: two head groups, staged local prefill, graph-shared borrowed output.
This is a comparison of complete experimental paths, not stock NCCL vs overlap.
H3 captures the original 50-block stack, Qwen the original 60-block stack after
model preparation, and FLUX/Wan the declared transformer forward. Eager reference
vs graph and serial vs overlap must be bitwise equal. Captures must reach direct
CE with no fallback. Replays have no Python native calls, as expected.
H3 uses six fixed PDD steps, Qwen eight steps, FLUX four steps and Wan eight
steps with CFG 1. Qwen requested true_cfg_scale=4 but had no negative prompt,
so its actual path was single-branch. The earlier 'true CFG 4' description
was incorrect; timing samples are unchanged. No approximate step cache is enabled.
H3 uses its native VAE tile parallelism over SP ranks; the other families request
VAE patch parallelism 2. H3 SP4 also uses text-encoder TP4; SP2 uses TE TP2.
Runtime clarification (2026-11-21): Qwen and FLUX registry logs explicitly
ignore the requested VAE2 because these pipeline VAEs lack DistributedVaeMixin.
Their measurements must not be described as effective VAE2. Wan's distributed
VAE path is supported. See COVERAGE-RESULTS.txt for the expanded runtime audit.
Quantized rows use online FP8 DiT linears with BF16 attention/CE.

Interpretation and limitations
H3 SP4's 30-pair confirmations repeat the direction and magnitude of the earlier
eight-pair run. BF16 SP2 at 2K/3K/4K also improves, with only four pairs per case.
Qwen-Image-Edit has no stable gain across the tested reference-image cases.
Wan5B's four cases range from -0.83% to +1.13%, with only 1-3 of four pairs
faster per case; no stable gain is accepted. Requested 720x1280 rounds to
704x1280 in the existing pipeline; the output-shape column records that.
Its global attention lengths are 1950/3510/6630/7920, so video frame count
alone does not imply a larger attention workload than the high-resolution H3 cases.
FLUX 2K/ref1 initially reported 7.71% in four pairs while absolute times drifted
from about 2.2 to 3.0 seconds; that magnitude did not reproduce. Its 30-pair
confirmation was 2134.520 -> 2115.910 ms (0.87%, 27/30 faster). This supports
a small positive direction, substantially below the exploratory median ratio.
FLUX FP8 initialization rejects its current linear quantization path, so its valid
comparisons are explicitly BF16. FLUX ref2 fails in the existing image-latent ID
preparation before attention; the completed text/ref1 cases are retained separately.
Failed initialization and rejected non-CE captures are never counted as speedups.
NPU, hybrid parallelism, multiple concurrent requests and HTTP serving are untested.

Communication share
Per the latest request, no new communication profiles were collected. All new
communication_share fields are null; they cannot be inferred from E2E deltas.
Historical H3-Image 2K/SP2 graph evidence (rank0, request1, six steps): outgoing
P2P CE activity was 49.261 ms over 793.163 ms of summed block-stack device spans,
or 6.21%. This is outgoing P2P / DiT window, not all communication / request.
Its P2P activity outside local FA3 fell from 49.261 to 28.412 ms (42.3%) in the
staged/per-layer-slot experiment. Bytes did not decrease. Those older trace
fractions are not assigned to SP4, new resolutions or other models.

Code and verification
The native plan cache retains up to 16 live layouts until graphs are destroyed;
one following layout cannot replace storage referenced by a resident graph.
Known dense Wan geometry metadata passes through unchanged; unknown sparse
metadata still rejects the overlap route. Necessary peer fences remain intact.
The public head-chunk knob is now declared across CLI, orchestrator, engine and
deploy schemas. Registered Wan previously lost nested parallel_config, then lost
the undeclared head_chunks field; actual runtime audits exposed both failures.
GPU layout QA: SP2 and SP4, three resident dense/joint graphs, eight alternating
replays under asymmetric delay, bitwise exact; global-reference distributed suite
passes without skips. Latest SP4 QA also covers dense geometry admission.
Argument regressions: 9 passed, 675 deselected. Ruff/format, torch.cuda and
forbidden-import checks passed on the changed Python files.
Source SHA and measured-source hashes are attached per run in the JSON. The first
H3 SP2 FP8 sweep predates the cache-key/dtype guards; its transfer and scheduling
kernels match the later version. All other completed model runs use the current
native CE core. Scripts and integration patches remain explicit experiment tools.
The final Wan rerun uses a task-local Triton cache after the shared cache
raised OSError 116 (stale file handle); quantization and VAE parallelism stay enabled.
